# 软件开发团队 · ZCode 插件交付说明与审查报告

本目录是一个 ZCode 本地插件市场的根目录，内含「软件开发团队」插件源码（版本 **0.2.1**）：在 ZCode 里召唤一支由**交付总监**带队的研发专家团——产品经理定需求、架构师做设计+拆任务、工程师批量并行实现代码、QA 做集成验收，小需求支持快速模式。0.2.1 起需求与方案文档受预算约束，审校为单轮短上下文，检查门禁由工作流确定性执行。

本文档分两部分：**交付说明**（目录结构、安装、使用、验收）与**审查与优化报告**（这次为什么改、怎么改的、验证到什么程度、还剩哪些限制）。

## 一、交付说明

### 交付内容

```text
zcode/                                   ← 本地测试市场根目录（粘贴到 ZCode 的就是它）
├── marketplace.json                     市场清单（市场名 dev-zcode-215ecc2f，版本 0.2.1）
└── software-dev-team/                   插件源码（software-dev-team，版本 0.2.1）
    ├── .zcode-plugin/plugin.json        插件清单
    ├── commands/
    │   ├── dev-team.md                  召唤入口：完整模式 /dev-team
    │   └── dev-team-fast.md             召唤入口：快速模式 /dev-team-fast
    ├── skills/software-dev-team/
    │   ├── SKILL.md                     交付总监手册：召唤协议、模式与成本预期、结果转述、失败排查、红线
    │   └── references/                  五个角色的职责文档
    │       ├── delivery-director.md       交付总监（主会话 + 短上下文审校）
    │       ├── product-manager.md         产品经理
    │       ├── architect.md               架构师
    │       ├── engineer.md                工程师
    │       └── qa.md                      QA 工程师
    ├── workflows/
    │   └── software-dev-team.dwf.ts      团队流水线（完整/快速双模式）
    ├── CHANGELOG.md                     0.2.1 变更清单与实测依据
    └── README.md                        插件自身说明
```

两种模式的流水线：

- **完整模式**：产品经理界定需求（预算受控）→ 交付总监审校需求（短上下文单轮）→ 架构师设计并拆任务（任务自包含）→ 交付总监审校方案（短上下文单轮）→ 工程师按依赖波次并行实现 → 确定性检查（测试/构建/静态检查）→ QA 集成验收（不过则一轮修复）→ 确定性汇总交付报告。
- **快速模式**：技术负责人（产品+架构二合一）一次产出需求与方案 → 一次快审 → 工程师并行实现 → 确定性检查 → QA 集成验收 → 汇总。

### 安装步骤

1. 打开 **插件市场 / Plugin Marketplace** → **添加 / Add → 添加插件市场 / Add Plugin Marketplace**。
2. 粘贴市场根目录：`D:\web\dev-team\zcode`（就是本 README 所在的目录），点击添加。
3. 添加成功后进入 **个人 / Personal**，找到「软件开发团队」（版本 0.2.1），点击 **安装 / Install**。
4. 安装后可在 **设置 → 插件 / Settings → Plugins** 管理启用状态。

后续更新：在市场源里点该市场的**刷新**，再到「个人」里对插件点**更新**；源码改动不会热更新，必须走这两步。

### 使用方式

安装后新建任务，在输入框直接召唤：

- `/dev-team <需求描述>` —— 完整模式，适合涉及多个模块、要改多处代码、有集成风险的需求；
- `/dev-team-fast <需求描述>` —— 快速模式，适合单一目标、一两个文件能搞定的小需求。

拿不准就用完整模式。运行期间主代理以交付总监身份工作：提交工作流、回答子代理的阻塞问题、结束时按「结论 / 问题 / 已验证 / 未覆盖」如实转述，不重跑整轮、不隐瞒未覆盖项。

### 验收方式

安装后新建任务，输入：

```text
/dev-team 做一个本地待办清单 CLI：支持添加、列出、完成待办，数据存在 JSON 文件里，带单元测试
```

预期可观察结果：

1. 工作流按七个阶段推进：需求界定 → 需求审校 → 设计拆任务 → 方案审校 → 并行实现 → 确定性检查 → 集成验收，之后在工作流内确定性地组装交付报告；
2. 任务看板逐个任务翻状态，同波次任务并行推进；
3. 仓库中生成 `docs/dev-team/prd.md`（需求与 AC-01… 编号的验收标准）和 `docs/dev-team/design.md`（方案与自包含任务拆分）；
4. 结束产出交付报告卡片：逐条 AC 结论表、审校记录、QA 结论、各任务完成情况、检查命令与退出码、未覆盖项；
5. 结论分清「已验证」与「未覆盖」——没跑或跑不了的检查会明说，不会装作没问题；可交付与否由确定性规则给出，不靠子代理表态。

小需求可再试一次快速模式对比：

```text
/dev-team-fast 写一个华氏度转摄氏度的命令行脚本，带 pytest 测试
```

### 备注

- `docs/dev-team/` 是团队每次运行重新生成的产出；若目标仓库的 `.gitignore` 没有忽略它，请自行加一条（需要留存需求文档溯源就放开）。
- 工作流脚本的完整类型检查在首次 `/dev-team` 提交时由 ZCode 工作流编译器完成；若收到编译诊断，按提示修正 `workflows/software-dev-team.dwf.ts` 后重新提交即可。
- 本目录为本地测试市场，不等于公开发布；换机器使用需重新执行上面的添加步骤。
- 0.2.1 的变更细节与实测依据见 `software-dev-team/CHANGELOG.md`。

## 二、审查与优化报告（0.1.x → 0.2.1）

> 触发原因：一次「本地待办清单 CLI」完整模式运行耗时 **1 小时 22 分**、消耗 **约 1800 万 token**。
> 结论：根因不是模型慢，而是**工作流结构把每一轮验证与每一份文档重复读进上下文**。0.2.1 通过删冗余验证层、给文档与验收标准设预算、把审校换成短上下文、把质量门禁改成确定性执行来降本，同时修掉 13 个会导致「假通过 / 整轮作废」的真实缺陷。

### 2.1 基线：三次真实运行的钱花在哪

数据来源：ZCode 本地运行库 `~/.zcode/cli/db/db.sqlite`（`dwf_run` / `dwf_actor` / `dwf_node` / `model_usage`），按库内 provider 上报复算。

| 运行 | 状态 | token | 墙钟 | 说明 |
| --- | --- | --- | --- | --- |
| run 1 | failed | 12,927,801 | ~87 分钟 | `world.run("npm")` spawn ENOENT 未捕获，整轮失败，token 全废 |
| run 2 | resumed（续 run 1） | 净增 13,872,897（账本累计 26,800,698） | 81 分钟 | 7 任务 + 7 质检 + 29 条 AC |
| run 3 | completed（独立重跑） | 18,632,646 | 82 分钟 | 10 个会话、15 次 ask、39 条 AC；PRD 32,428 字节、design 29,882 字节 |
| **合计** | | **45,433,344（约 45.4M）** | **约 4 小时 10 分** | run 2 的累计值含 run 1，不能重复计 |

run 3 的 18.63M 里，**92.8% 是缓存命中的重复输入**，真正新增只有 1.34M（7.2%），模型输出仅 0.40M（2.2%）。也就是说：**钱几乎全花在「反复读上下文」，不是写代码。**

五个放大器（按占比）：

| # | 机制 | 证据 | 占 18.63M |
| --- | --- | --- | --- |
| M1 | 需求文档被打回两次、整体重写两次 | 两次 ask 分别 4,208,235 + 2,481,749；PM 全程 99 次请求、41 次 Edit + 50 次 Bash 都在改 32KB 的 prd.md | 35.9% |
| M2 | 交付总监是持久会话，4 轮审校上下文逐轮累积 | 每次 ask 首请求输入 19,628 → 65,688 → 113,686 → 175,563，末请求 213,023 | 16.8% |
| M3 | 每个任务配一名质检员，3 轮共 0 次打回 | 2,812,089（60 次请求、74 次工具调用） | 15.1% |
| M4 | 门禁没认出 `tests/test_todo.py`（`checkKeys=[]`），QA 与终验只能手工全量复验 | QA 1,068,279 + 终验 1,831,166 | 15.6% |
| M5 | 39 条 AC 对应 3 个命令，AC 清单 19,382 字符占终验提示词 99.9% | 终验逐条重跑 39 条 | 9.8% |

外加两个结构性原因：全串行（15 个 ask 首尾相接，0 并发），每请求固定基线 15,750 token × 287 次请求 ≈ 4.5M。

> 注：面板上的 token 含缓存命中输入，实际计费按缓存价折算，「18.6M」不等于等额费用；但它真实反映了**上下文被重复搬运的次数**，优化目标同时压低面板数字与真实输入/输出量。

### 2.2 结构性降本（砍重复验证，不是砍验证）

| 机制 | 旧版 | 0.2.1 |
| --- | --- | --- |
| 需求文档 | 无预算，32KB / 39 条 AC | 规模分级 + 字符预算 + AC 预算（small/medium/large），机械校验，超限一次压缩修订 |
| 方案文档 | 约 30KB，工程师还要读 | ≤6000 字符（medium 软上限），信息前置到任务步骤，工程师不读 |
| 需求/方案审校 | 同一个持久总监会话，最多两轮打回 | 两个**全新短上下文**子代理，各一轮封顶；打回后修订一次即继续并记 `reviewWarnings` |
| 逐任务质检 | 每任务一名质检员（2.81M，约 15%） | **删除**；门禁之后做一次集成验收 |
| LLM 终验 | 总监子代理重跑 39 条 AC（1.83M） | **删除**；结论由确定性规则 + QA 逐条证据算出 |
| 工程师交接 | 读 PRD/design.md、跑全量测试 | 任务自包含；读文件 ≤5 个、自检命令 ≤3 条，不跑全量 |
| 机械校验 | 靠模型自我约束与重试 | 零 token 的确定性校验：AC 条数/字符、任务数、依赖环、同波文件冲突、任务自包含、检查项合法性 |
| 修复轮 | 分诊 + 多轮修复 | **一轮**；只重跑失败门禁；QA 同会话复核只更新受影响 AC |

### 2.3 修掉的 13 个真实缺陷

前 5 个会直接导致「错误结论」或「整轮作废」：

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `world.run("npm")` spawn 失败未捕获 | 整轮 failed，12.9M token 作废 | 所有命令执行统一捕获；spawn 失败/超时/命令缺失记 `unavailable`，继续交付 |
| 2 | npm 回退把**超时**也 catch 后改跑 `npm.cmd` | 多等一个超时周期，命令有副作用时重复执行 | 只在 spawn 失败时回退；超时单独记 `unavailable` |
| 3 | 「命令不可用」靠**输出文本**判断 | 被测程序的 traceback（`No such file`/`ENOENT`）会让**真实失败**被降级成「不可用」→ 红测试不进 findings、不阻断交付 | 删除文本猜测：`unavailable` 只来自 spawn 失败、超时、零用例 |
| 4 | 测试「收集到 0 个用例」且退出码 0 | 被记成检查通过（假质量信号） | 识别 `Ran 0 tests`/pytest exit 5/`running 0 tests`/`no test files`/`no test specified`/`# tests 0` → 记「不可用」并进未覆盖项 |
| 5 | 任一 `ask` 失败即整轮崩 | 结构化输出校验反复不过时，已花 token 全作废 | 所有 `ask` 统一兜底：产品经理/技术负责人失败 → 出中断报告；审校失败 → 记审校警告；工程师失败 → 任务标记未完成并阻断交付 |
| 6 | 只有 `test/` 目录的 Python 项目必然 ImportError | 误判不可交付，还白跑一轮修复 | 自动识别 `tests/` 或 `test/`，命令目录与探测一致 |
| 7 | npm init 默认测试脚本被当门禁 | 误判不可交付 | 探测阶段跳过占位脚本；显式选中时按输出记「不可用」 |
| 8 | QA 复核「整体替换」结论 | 没提到的 AC 条目丢失 | QA 结论按 AC 编号合并 |
| 9 | 修复工程师的改动不进复核与报告 | 用户看不到修复轮改了什么 | 摘要进复核 prompt 与交付报告 |
| 10 | `deliverable` 只看 `qaVerdict.pass` | QA 自相矛盾（pass=true 却留着 high 问题）时仍判可交付 | 追加「无未解决 high/medium 问题」「无失败任务」两个条件 |
| 11 | 审校两轮耗尽后仍假放行 | 静默放行 | 单轮封顶 + 打回意见进 `reviewWarnings` 与报告 |
| 12 | 依赖成环时按数组顺序硬跑 | 依赖语义被违反 | 成环显式 log + 进预算警告，调度退化为单任务串行（不并发改同一文件） |
| 13 | 单批并发可能超过宿主上限 | 触发并发限制 | 单批再切一刀，最多 5 个并发 |

交付判定改为确定性规则，不再靠子代理表态：

```
可交付 = QA 通过
       + 全部 AC 有通过证据（无未通过、无缺证据）
       + 无未解决的高/中严重度问题
       + 无失败门禁（unavailable 不算失败，但必须进未覆盖项）
       + 无因请求失败未完成的任务
       + 有可执行任务 + 有验收标准
```

### 2.4 产出目录调整

需求与方案文档从 `.dev-team/` 改到 **`docs/dev-team/`**：`docs/dev-team/prd.md`、`docs/dev-team/design.md`。

- 脚本读取（PRD 回读、方案回读、`AmendWorkflow` 兜底恢复需求）、审校输入、机械校验、artifact 发布、修复轮提示全部指向新路径；

- 目标仓库的 `.gitignore` 请把 `.dev-team/` 换成 `docs/dev-team/`。

### 2.7 剩余限制（发布前已知）

- 上面的数字是目标而非实测；在复测前不要对外宣称「已降低」的具体比例。
- 检查菜单之外的生态（例如 .NET、Maven）没有专用命令，只能留空走自动探测；没有可用检查时会在 `notCovered` 里明说。
- 「不可用」只由三种情况产生：命令 spawn 失败、命令超时、测试命令没有收集到任何用例；不用输出文本猜命令缺失——被测程序的 traceback 里常有 `No such file`/`ENOENT`，那样会把真实失败误判成「不可用」而假通过。
- 同一个工作流文件同时含完整模式与快速模式的阶段标记，提交审批时审批图会把另一分支的阶段也列出来；不影响执行。
- 架构师给出的任务若依赖成环，调度器会退化成「按数组顺序单任务串行推进」并把成环写进预算警告——此时依赖语义不被满足。
- 子代理请求失败现在会降级：产品经理/技术负责人失败 → 直接出中断报告；审校失败 → 记审校警告并继续；工程师失败 → 该任务标记未完成并阻断交付。降级会保留已完成部分，但那一轮不会产出可交付结果。
- 交付判定里的「QA 没有未解决的高/中严重度问题」依赖 QA 如实填写 `severity`；QA 自相矛盾（`pass=true` 却留着 high 问题）会被规则拦住，但 QA 整体漏报问题不在规则覆盖范围内。
- 0.2.1 尚未做真机端到端运行；上面的成本与时长都是目标区间。

### 2.8 复测步骤

1. 在 ZCode 里刷新插件市场 → 「个人」→ 更新「软件开发团队」（源码不热更新，必须更新到 0.2.1）。
2. 新建任务，用同一类需求复测：`/dev-team 做一个本地待办清单 CLI：支持添加、列出、完成待办，数据存在 JSON 文件里，带单元测试`。
3. 重点观察：会话数（3 任务应为 8 个会话、8 次左右 ask）；`docs/dev-team/prd.md` 是否只有几千字符、AC 条数是否 ≤14；是否自动跑起 unittest（`tests/` 目录）、门禁退出码；交付报告里「已验证」与「未覆盖项」是否分开写清楚。
4. 复测后按同一口径对比 token：本地运行库 `~/.zcode/cli/db/db.sqlite` 的 `dwf_run.spent_tokens` 即是总账，分角色明细在 `dwf_actor` / `model_usage`。
