# 更新日志（CHANGELOG）

## 0.2.1

> 版本说明：仓库里的上一版插件是 **0.1.0**；中间的 0.2.0 只是内部工作版本、从未发布，因此本次直接以 **0.2.1** 发布，0.2.1 一次性包含下列全部改动。

0.2.1 的核心取舍：把「多层大模型复验」换成「确定性门禁 + 逐条验收证据 + 未覆盖披露」，同时给文档体积、审校上下文和任务交接方式设上预算。改动分三类记录。

相对 0.1.0 的两点版本级变化：

1. **产出目录**：需求与方案文档从 `.dev-team/` 改到 **`docs/dev-team/`**（`prd.md`、`design.md`），放在仓库里可见、可追溯；目标仓库的 `.gitignore` 建议把 `.dev-team/` 换成 `docs/dev-team/`。
2. **版本一致性**：两份清单（`marketplace.json`、`.zcode-plugin/plugin.json`）与全部文档统一为 0.2.1；0.1.0 时代「清单写 0.1.0、装出来的却是 0.1.1」的漂移不再存在。

### 一、修了什么 bug

| # | 问题 | 根因 | 0.2.1 处理 |
| --- | --- | --- | --- |
| 1 | 一次完整模式运行因 `world.run("npm")` spawn 失败（ENOENT）整轮 failed，12,927,801 token 全部打水漂 | 命令执行没有兜底，任何 spawn 异常都会冒泡终止工作流 | 所有命令执行都做异常捕获；spawn 失败、命令不存在、超时记为 `unavailable` 或 `findings`，工作流继续交付 |

| 6 | 运行失败与质量结论混在一起：`world.run` spawn 失败会冒泡终止整轮；质量结论又没有确定性判定规则，是否可交付取决于子代理表态 | 缺少命令级异常兜底，也缺少「结论由证据算出」的判定规则 | 命令执行全部兜底；交付结论改为确定性规则计算，其余问题进 `findings` / `notCovered`，运行本身继续到交付 |
| 7 | 工程师需要读 PRD 与 design.md 才能开工，方案文档成为反复读取的成本载体；任务里还会出现「见 design.md §x」 | 任务不自包含，交接靠路径 | 任务说明自包含（文件、步骤、本任务 AC、依赖摘要），机械校验禁止在步骤/AC 中出现 `docs/dev-team/` 或 `design.md` 引用；工程师不再读团队文档 |
| 8 | npm 的回退逻辑把**超时**也 catch 后改跑 `npm.cmd`：一次超时会被当成「npm 不可用」再等一个超时周期，命令有副作用时还会重复执行 | 回退条件写成了「所有异常」，而不是「spawn 失败」 | 只在 spawn 失败（ENOENT / not recognized 等）时回退 `npm.cmd`；超时与命令缺失记为「不可用」进未覆盖项，不判代码失败 |

### 二、砍了什么成本

| 机制 | 0.1.1 | 0.2.1 |
| --- | --- | --- |
| 需求文档 | 无预算，实测 32KB / 39 条 AC | 规模分级（small/medium/large）+ 字符预算 + AC 预算，机械校验，超限一次压缩修订 |
| 方案文档 | 约 30KB，工程师还要读 | ≤6000 字符（medium 软上限），信息前置到任务步骤，工程师不读 |
| 需求/方案审校 | 持久总监，最多两轮打回 | 全新短上下文，各一轮封顶 |
| 逐任务质检 | 每任务一名质检员，实测 2.8M token（约 15%） | 删除；门禁之后做一次集成验收 |
| LLM 终验 | 总监子代理重跑 39 条 AC（1.83M token） | 删除；交付结论由确定性规则 + QA 逐条证据得出 |
| 工程师交接 | 读文档、跑全量测试 | 自包含任务；读文件 ≤5 个、自检命令 ≤3 条，不跑全量 |
| 规则校验 | 靠模型自我约束与重试 | 机械校验（零 token）：PRD 与设计的问题清单、预算、依赖环、同波文件冲突 |
| 修复轮 | 分诊 + 多轮修复 | 一轮修复；只重跑失败门禁；QA 同会话复核只更新受影响 AC |

### 三、质量门禁如何不降级

0.2.1 去掉的是「重复验证」，不是「验证」：

1. **交付判定确定化**：可交付 = QA 通过 + 全部 AC 有通过证据 + 无缺证据 AC + 无失败门禁 + 有任务 + 有 AC。六项齐全才叫可交付，任一缺口都会在结论里报出数量，不靠子代理表态。
2. **确定性门禁**：检查命令由工作流统一执行并逐项记录命令、退出码、输出；不可用项标 `unavailable` 并进未覆盖项，不当作通过。检查菜单 + 自动探测覆盖 Node、Python（pytest/unittest）、Rust、Go。
3. **QA 逐条 AC 证据**：每条 AC 必须有结论与证据（`id` 回填 AC-01…），缺编号要求补齐一次；问题条目用 `status` 区分「确定性检查确认」与「仅审阅未复核」。
4. **一轮修复闭环**：验收不通过 → 定位到任务后由对应工程师修（或新建修复工程师）→ 只重跑失败门禁 → QA 同会话复核，只更新受影响 AC 与问题。
5. **未覆盖项强制披露**：验收缺口、不可用检查、审校警告、预算警告全部进 `notCovered` / `findings`，不允许写成「无」。
6. **红线保留**：不谎报命令与文件；不删测试、不改断言、不注掉逻辑来「让检查通过」；QA 只读不改；工程师不超范围改动。

### 四、实测依据（0.1.1 基线）

以下是 0.1.1 在真实需求上的三次运行，只作为基线，**不是 0.2.1 的实测结果**。注意 run 2 是 run 1 的续跑：它的账本累计 26,800,698 已包含 run 1 的 12,927,801，自身净增 13,872,897。

| 运行 | 状态 | token | 墙钟 | 备注 |
| --- | --- | --- | --- | --- |
| run 1 | failed | 12,927,801 | 约 87 分钟 | `world.run("npm")` spawn ENOENT 未捕获，整轮失败 |
| run 2 | resumed（续 run 1） | 净增 13,872,897（账本累计 26,800,698） | 81 分钟 | 7 个任务 + 7 个质检 + 29 条 AC |
| run 3 | completed（独立重跑） | 18,632,646 | 82 分钟 | 10 个会话、15 次 ask、39 条 AC；PRD 32,428 字节、design 29,882 字节 |

三次实际净消耗合计 **45,433,344 token（约 45.4M）**，约 4 小时 10 分钟。run 3 的分角色消耗：产品经理 7.52M、交付总监 3.13M、架构师 1.35M、3 名工程师 + 3 名质检合计 5.56M、QA 1.07M。同一类需求（3 命令待办 CLI）上，旧版 39 条 AC、PRD 32KB、design 30KB，是成本放大的主因。

### 五、0.2.1 目标区间（目标，待真机复测）

| 场景 | 预计会话数 | 预计 token | 预计墙钟 |
| --- | --- | --- | --- |
| 快速模式（1 任务，小需求） | 4 | 0.5–1.2M | 6–15 分钟 |
| 完整模式 small（2 任务） | 7 | 1.0–2.5M | 10–20 分钟 |
| 完整模式 medium（3 任务，待办 CLI 同类） | 8 | 1.7–3.5M | 15–30 分钟 |
| 完整模式 large（6–8 任务） | 11–13 | 4–9M | 30–60 分钟 |

区间来自两套口径的交叉：离线仿真（用 0.1.1 真实请求校准）给出 medium 3 任务中性 1.71M / 保守 2.55M；独立成本审计按旧版每请求工作量外推给出保守档 5.3–6.8M。仿真乐观、审计保守，因此上表取两者之间的区间，并把审计档视为上限。会话数按子代理上下文数计（不含主会话）：完整模式 = 任务数 + 5（产品经理 + 需求审校 + 架构师 + 方案审校 + N 名工程师 + QA）；快速模式 = 任务数 + 3（技术负责人 + 快审 + N 名工程师 + QA）；修复轮若派出「修复工程师」再 +1。以上均为**目标区间**，尚未经过 0.2.1 端到端复测；最终以真机复测为准。

### 六、兼容性与升级

- 工作流参数不变：`requirement`（必填）、`mode`（默认 `full`）；不新增模型或预算参数。
- 召唤入口不变：`/dev-team`、`/dev-team-fast`。
- 角色变化：取消「质检员」与终验子代理；审校改为全新短上下文（完整模式需求/方案各一名，快速模式一名合审）；QA 改为门禁之后的一次集成验收。`references/` 五份角色手册已按新职责重写。
- `docs/dev-team/prd.md` 与 `docs/dev-team/design.md` 仍是每次运行重新生成的产出；**0.2.1 把产出目录从 `.dev-team/` 改为 `docs/dev-team/`**（放在仓库里可见、可追溯，不再是隐藏目录）。目标仓库的 `.gitignore` 若还留着 `.dev-team/`，建议换成 `docs/dev-team/`。
- 升级方式不变：插件市场刷新该市场 → 在「个人」里对插件点更新。

### 七、已知限制

- 第五节的数字是目标而非实测；在复测前不要对外宣称「已降低」的具体比例。
- 检查菜单之外的生态（例如 .NET、Maven）没有专用命令，只能留空走自动探测；没有可用检查时会在 `notCovered` 里明说。
- 「不可用」只由三种情况产生：命令 spawn 失败、命令超时、测试命令没有收集到任何用例（unittest `Ran 0 tests`、pytest exit 5、cargo `running 0 tests`、go `no test files`、npm `no test specified`、node-test `# tests 0`）。不用输出文本猜命令缺失——被测程序的 traceback 里常有 `No such file`/`ENOENT`，那样会把真实失败误判成「不可用」而假通过。
- 同一个工作流文件同时含完整模式与快速模式的阶段标记，提交审批时审批图会把另一分支的阶段也列出来；不影响执行。
- 架构师给出的任务若依赖成环，调度器会退化成「按数组顺序单任务串行推进」并把成环写进预算警告——此时依赖语义不被满足，属于方案缺陷被机械校验打回后的兜底行为。
- 子代理请求失败（结构化输出校验反复不过）现在会降级：产品经理/技术负责人失败 → 直接出中断报告；审校失败 → 记审校警告并继续；工程师失败 → 该任务标记未完成并阻断交付。降级会保留已完成部分，但那一轮不会产出可交付结果。
- 交付判定里的「QA 没有未解决的高/中严重度问题」依赖 QA 如实填写 `severity`；QA 自相矛盾（`pass=true` 却留着 high 问题）会被规则拦住，但 QA 整体漏报问题不在规则覆盖范围内。
