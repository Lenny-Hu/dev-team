# 软件开发团队（software-dev-team）0.2.1

在 ZCode 里召唤一支像专家团一样的软件开发团队：**交付总监**带队，产品经理定需求、架构师做设计+拆任务、工程师批量并行实现代码、QA 做集成验收；小需求支持快速模式。0.2.1 起，需求与方案文档有预算约束，审校是单轮短上下文，检查门禁由工作流确定性执行。

## 组成

| 组件 | 说明 |
| --- | --- |
| `commands/dev-team.md` | 召唤入口（完整模式）：`/dev-team <需求描述>` |
| `commands/dev-team-fast.md` | 召唤入口（快速模式）：`/dev-team-fast <小需求描述>` |
| `skills/software-dev-team/SKILL.md` | 交付总监手册：召唤协议、模式选择与成本预期、结果转述、失败排查、红线 |
| `skills/software-dev-team/references/` | 五个角色的职责文档（交付总监/产品经理/架构师/工程师/QA） |
| `workflows/software-dev-team.dwf.ts` | 团队流水线：需求 → 审校 → 设计拆任务 → 审校 → 并行实现 → 确定性检查 → 集成验收 → 汇总 |
| `CHANGELOG.md` | 0.2.1 变更清单与实测依据 |

## 角色

| 角色 | 职责 |
| --- | --- |
| 交付总监（主会话） | 立项、提交工作流、运行期答疑、失败排查、把结果如实转述给用户；不重跑工作流、不重新核对 AC |
| 交付总监·需求审校 | 工作流新建的短上下文子代理：只读 PRD，单轮，最多 3 条阻塞意见 |
| 交付总监·方案审校 | 同上：只读任务表与检查项，单轮 |
| 交付总监·快审（仅快速模式） | 工作流新建的短上下文子代理：合起来审一次需求与方案 |
| 产品经理 | 把需求写成带规模分级与预算的 PRD |
| 架构师 | 技术方案、任务拆分（任务自包含）、检查菜单选择 |
| 工程师（每任务一名） | 按自包含任务说明实现代码，不读团队文档、不跑全量测试 |
| 修复工程师（按需） | 问题定位不到具体任务时统一修复 |
| QA 工程师（一名） | 唯一功能验收者：门禁之后按 AC 编号逐条给证据，门禁不重复跑 |
| 技术负责人（仅快速模式） | 产品经理 + 架构师二合一，一次产出需求与方案 |

0.2.1 取消了「质检员」：不再逐任务质检，改为门禁之后的一次集成验收（理由与质量保证见 `references/qa.md`）。

## 两种模式

### 完整模式（full）

1. **产品经理界定需求**：产出 `docs/dev-team/prd.md`，按 `small`/`medium`/`large` 选规模，受 AC 与字符预算约束；机械校验不合格则同会话一次修订。
2. **交付总监审校需求**：全新短上下文，只读 PRD（为确认可行性最多再读 2 个仓库文件），单轮；不通过则产品经理修订一次，之后记录审校意见继续。
3. **架构师技术设计与任务拆分**：产出 `docs/dev-team/design.md`，任务自包含；机械校验 id 唯一、依赖无环、同波文件不冲突、预算与步骤自包含。
4. **交付总监审校方案**：全新短上下文，只读任务表、检查项与方案摘要（最多再读 design.md 一次），单轮。
5. **工程师按批次并行实现**：按依赖波次并行，每任务一名工程师，任务说明了文件、步骤、本任务 AC 与依赖摘要。
6. **确定性检查**：按检查菜单执行测试/构建/静态检查，逐项记录命令与退出码；不可用的命令记为 `unavailable`，不判失败。
7. **集成验收**：一名 QA 对照 AC 编号逐条给证据；不通过则一轮修复（复用相关工程师或新建修复工程师），只重跑失败门禁，再同会话复核。
8. **交付汇总（不是独立阶段）**：确定性组装交付报告（逐条 AC 结论表、审校记录、QA 结论、检查结果、未覆盖项），返回 `WorkflowReport`（结论 / 问题 / 已验证 / 未覆盖），不设大模型终验。

### 快速模式（fast）

技术负责人一次产出需求与方案（两份文档）→ 机械校验 + 一次修订 → 一次快审 → 并行实现 → 确定性检查 → 集成验收 → 汇总。适合单一目标、一两个文件、无集成风险的小需求。

## 工作流产出

- `docs/dev-team/prd.md`：需求文档（背景、规模、用户故事、逐条 AC、非目标、假设、风险）
- `docs/dev-team/design.md`：技术方案与任务拆分（方案摘要、约定、任务清单、检查项、风险）
- 交付报告（artifact 主卡片：逐条 AC 结论表、审校记录、QA 结论、任务完成情况、检查命令与退出码、未覆盖项）
- 任务看板（实时显示每个任务处于 实现中 / 需修复 / 已完成；终态由交付结论决定）

## 质量约定

- 交付判定是确定性的：QA 通过 + 全部 AC 有通过证据 + 无缺证据 AC + 无失败门禁 + 有任务 + 有 AC，六项齐全才算「可交付」；
- 项目检查命令（node / pytest / unittest / cargo / go）由工作流统一执行并记录退出码，QA 不重复跑；
- QA 按 AC 编号逐条给证据，缺编号会要求补齐一次；
- 验收不通过或门禁仍有失败项时只修一轮，且只重跑失败的门禁项；
- 不可用检查、验收缺口、审校与预算警告全部写进报告，不写成「无」；
- 任何角色不得谎称跑过没跑的命令；工程师不得删测试、改断言、注掉逻辑来「让检查通过」。

## 预期成本与时长（目标区间）

| 场景 | 预计会话数 | 预计 token | 预计墙钟 |
| --- | --- | --- | --- |
| 快速模式（1 任务，小需求） | 4 | 0.5–1.2M | 6–15 分钟 |
| 完整模式 small（2 任务） | 7 | 1.0–2.5M | 10–20 分钟 |
| 完整模式 medium（3 任务，待办 CLI 同类） | 8 | 1.7–3.5M | 15–30 分钟 |
| 完整模式 large（6–8 任务） | 11–13 | 4–9M | 30–60 分钟 |

会话数按子代理上下文数计（不含主会话）：完整模式 = 任务数 + 5；快速模式 = 任务数 + 3；修复轮若派出修复工程师再 +1。以上为**目标区间**，依据 0.1.1 的运行记录推算（三次运行实际净消耗合计约 45.4M token：run 1 失败 12,927,801，run 2 续跑净增 13,872,897，run 3 独立重跑 18,632,646；最后一次 82 分钟、10 个会话、39 条 AC），尚待 0.2.1 真机复测。实际成本受需求规模、仓库大小、检查命令耗时影响。

## 安装（本地测试市场）

市场根目录：`D:\web\dev-team\zcode`（含 `marketplace.json`）。
在 ZCode 中：插件市场 → 添加 → 添加插件市场，粘贴上述目录；然后在「个人」中找到「软件开发团队」安装。

## 验收一次

安装后新建任务，输入：

```text
/dev-team 做一个本地待办清单 CLI：支持添加、列出、完成待办，数据存在 JSON 文件里，带单元测试
```

预期可观察结果：

1. 工作流按七个阶段推进：需求界定 → 需求审校 → 设计拆任务 → 方案审校 → 并行实现 → 确定性检查 → 集成验收，最后在工作流内确定性地组装交付报告；
2. 任务看板逐个任务翻状态，同波次任务并行推进；
3. 仓库生成 `docs/dev-team/prd.md`（含 AC-01… 编号）与 `docs/dev-team/design.md`（任务自包含）；
4. 结束产出交付报告卡片：逐条 AC 结论表、审校记录、QA 结论、各任务完成情况、检查命令与退出码、未覆盖项；
5. 结论分清「已验证」与「未覆盖」——没跑或跑不了的检查会明说。

小需求可再试一次快速模式对比：

```text
/dev-team-fast 写一个华氏度转摄氏度的命令行脚本，带 pytest 测试
```

## 备注

- `docs/dev-team/` 每次运行重新生成；若目标仓库的 `.gitignore` 没有忽略它，请自行加一条（需要留存需求文档溯源就放开）。
- 工作流脚本的类型检查在首次提交时由 ZCode 工作流编译器完成；若收到编译诊断，按提示修正 `workflows/software-dev-team.dwf.ts` 后重新提交。
- 本目录为本地测试市场，不等于公开发布；换机器使用需重新执行添加步骤。
